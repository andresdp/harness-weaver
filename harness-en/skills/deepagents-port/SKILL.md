# DeepAgents Port — HarnessSpec or harness artifacts → DeepAgents runtime

This is the DeepAgents adapter. The shared HarnessSpec is the design authority when supplied; legacy Claude Code artifacts (`.claude/agents/`, `.claude/skills/`, orchestrator, `_workspace/` artifacts) are an optional input for migration. The adapter maps supported intent onto a **DeepAgents** runtime — one deep agent per stage, `AGENTS.md` memory, `skills/*/SKILL.md`, JSON artifacts on a virtual filesystem, deterministic sequencing in Python.

**This is generation, not line-by-line translation.** Claude Code–specific constructs (`SendMessage`, `Workflow` scripts, `subagent_type`, model tiers) have no DeepAgents equivalents; the port extracts the *team design* (roles, ordered tasks, artifact contracts, verification intent) and re-emits it in the target conventions. Never fake a mapping for something the target cannot express — surface it as a decision in the port report.

**Authoritative references for the target runtime — assume they are installed:** the official [langchain-skills](https://github.com/langchain-ai/langchain-skills) repository publishes curated skills for building Deep Agents applications (`deep-agents-core`, `deep-agents-orchestration`, `deep-agents-memory`, `langgraph-human-in-the-loop`, and the quickstarts). This skill assumes those skills are **installed and available to the coding agent performing the port**, so their guidance loads on demand while writing code:

```shell
npx skills add langchain-ai/langchain-skills --skill '*' --yes        # project-level
npx skills add langchain-ai/langchain-skills --skill '*' --yes --global
```

When generating or modifying any *Python-side* artifacts of the port — factory wiring, backend configuration, checkpointer setup, subagent definitions, interrupt/resume flows — consult the matching installed langchain-skills guidance first and follow its practices; `references/deepagents-target-pattern.md` covers the markdown-side conventions (stages, AGENTS.md, SKILL.md, JSON contracts) and defers to langchain-skills for everything code-side. If the skills are not installed, tell the user and offer to proceed from `references/deepagents-target-pattern.md` alone, flagging in the port report that code-side output was not cross-checked against the official guidance.

## When to use

- **Before generation** (Phase A): the user plans to build a harness that will later run on DeepAgents → advise a portability-aware design.
- **After generation** (Phase B): a harness exists (generated by the harness skill, tested in Claude Code) → port it.

Not for: designing a team from scratch (harness skill), or evolving an existing harness (evolve skill).

**HarnessSpec input:** When a HarnessSpec is supplied, treat it as the source of design intent and validate it with the available validator before generating stages. Record its path and version. If validation is unavailable, report that fact and do not claim the spec passed. If runtime artifacts are also supplied, compare them with the spec and surface conflicts instead of silently letting runtime conventions override it. Keep unsupported features and fidelity loss in `port-report.md`; do not change the shared spec to conceal adapter limits.

## Phase A — Portability-aware generation (pre-flight)

When consulted before the harness skill runs, recommend this generation prompt shape so the later port stays mechanical:

```
build a harness for <domain>. The work is a fixed sequential pipeline:
<stage 1> → <stage 2> → … . Use persistent agents sparingly — one orchestrator
plus one-shot sub-agents — and pass ALL data between steps as JSON files in
_workspace/ using the {NN}_{step}.json naming convention. Every step's skill
must document its input artifacts, its output JSON structure, and a read-back
verification rule. Keep verification as explicit skill steps, not as separate
messaging loops.
```

Why each clause matters for portability:

| Clause | Effect on the port |
|---|---|
| "fixed sequential pipeline" | Maps 1:1 to Python-stage sequencing; no `Workflow` script to discard |
| "pass ALL data as JSON files in `_workspace/`" | Harness's file-based data passing maps directly to `/artifacts/*.json` |
| "one orchestrator + one-shot sub-agents" | Avoids `SendMessage`-style collaboration that has no target equivalent |
| "input/output JSON structure + read-back rule in every skill" | Produces exactly the contract sections the target SKILL.md needs |
| "verification as skill steps" | Adversarial-verification intent survives as an intra-agent verification step |

Phase A ends with advice only. The user then runs the harness skill and tests the result in Claude Code.

> A fully worked Phase A example — the four-stage architecture decision pipeline — is in the repo docs: `docs/harness-100-prompts_EN.md`, appendix "portability-aware example".

## Phase B — Generate or port the DeepAgents form

Read `references/deepagents-target-pattern.md` first: it defines the target conventions this port must emit. Keep `references/mapping-table.md` open while mapping.

### B-0. Inventory the source

1. If a HarnessSpec is supplied, read it and apply the HarnessSpec input rules above. Record its path and version.
2. If existing runtime artifacts are supplied, inspect their trigger/history files, roles, skills, orchestrator phases, data-passing methods, verification patterns, and model rationale. Compare them with the spec and list conflicts; preserve domain intent from the spec and carry runtime-only behavior as a mapping decision.
3. If no spec is supplied, read the source runtime's instructions and artifacts plus any existing run outputs needed to understand behavior. Record the source paths and provenance in the port report.
4. If the source still uses v1 artifacts (`TeamCreate`, experimental flags), stop and run the harness skill's migration procedure first.

### B-1. Decide the stage boundaries

The target pattern is **one deep agent per stage; each stage runs N ordered skills**. When a spec is supplied, map its declared stages, roles, artifact contracts, verification, human gates, and runtime requirements onto it. When porting legacy artifacts without a spec, derive the map from the source and identify inferred details:

- Each orchestrator phase that produces a stable artifact set → **one stage** (`stage{N}-{name}/`).
- A harness *agent* is not necessarily a target *stage*: agents that only perform one task inside a phase usually collapse into that phase's **skill**. Agents embody *who*; the target cares about *what, in which order, writing which artifacts*.
- Parallel branches inside a phase: either serialize them (deterministic, matches the pattern's "one task at a time" rule) or flag for the subagent decision (B-2).

Record the stage plan: stage number, name, responsibility sentence, ordered task list, artifact filenames, upstream artifacts consumed, and source-spec references when available. Identify every requirement that cannot be represented in the target.

### B-2. Resolve decision points

For each item, decide once and apply consistently; record decisions in the port report:

| Decision | Default | Alternative |
|---|---|---|
| Agent-to-agent messaging (`SendMessage`) | Convert exchanges into artifact read/write steps | Enable DeepAgents subagents if the exchange is genuinely iterative |
| User confirmation points in the harness | Drop (the Claude-side gates don't apply at port time); if the *application* needs approval flows, add `HumanInTheLoopMiddleware` + checkpointer per langchain-skills `langgraph-human-in-the-loop` guidance | `interrupt_on` tool-level approval for artifact writes |
| Adversarial verification / judge panels | Intra-agent verification skill step (matches target pattern) | Dedicated verification stage between producer stages |
| `Workflow` scripts | Discard; sequencing moves to the Python pipeline + AGENTS.md ordered tasks | — |
| Model tiers (fable/opus/sonnet) | Single env-driven model; keep tier rationale as comments in AGENTS.md/skills | Map tiers to provider models (e.g. pro/flash) if the target supports per-agent models |
| Structured schemas (`schema`/`agentType`) | JSON structure block in each skill + Mandatory Completion Protocol in AGENTS.md | — |
| `CLAUDE.md` registry | Discard; the Python `stages.py` registry replaces it | Keep a domain README with the change-history table for evolve compatibility |

### B-3. Emit the target artifacts

For each stage, following `references/deepagents-target-pattern.md` exactly:

1. `stage{N}-{name}/AGENTS.md` — orchestrator memory: role header, responsibility, strictly ordered task list, Input Artifacts section, execution Rules (one task at a time; read the SKILL.md before each task; write artifact; read back and verify valid JSON; never skip; never parallel), scope boundaries (what this stage must NOT do), Mandatory Completion Protocol listing the stage's artifact filenames, post-task protocol.
2. `stage{N}-{name}/skills/{task}/SKILL.md` — frontmatter (`name`, `description`), Objective, Input Artifacts (paths), Procedure (numbered determinations), Rules with a Correct/Incorrect example pair, Expected Output (path + JSON structure block + read-back verification), and a boundary line ("Do not perform the next task").
3. JSON contracts: one artifact filename per task, snake_case, `{NN}_{step}.json` ordering consistent with the stage sequence; cross-stage references by ID fields (e.g. `source_requirement_ids`), never by prose.

Port over the harness skill *content* (procedures, rules, examples, evidence standards) — that is the design intelligence. Only the collaboration/runtime sections are rewritten.

### B-4. Emit the runtime wiring manifest

Generate `port-manifest.md` next to the emitted stages, containing the Python-side changes the application needs:

- `STAGES` registry entries: stage number → directory name + hand-off prompt (one sentence stating the stage's responsibility and what it consumes).
- `STAGE_ARTIFACTS` rows: stage number → list of artifact filenames the completion check should verify.
- Factory notes: memory/skills mount paths (`/agent/AGENTS.md`, `/agent/skills/`), backend routing (`/agent/` → read-only definition backend; everything else → project artifact store).
- Any decisions from B-2 that require application-level support (e.g. enabling subagents, per-agent models, approval flows via HumanInTheLoopMiddleware + checkpointer — following langchain-skills practices).

Do not modify the application's Python files unless the user asks; the manifest is the hand-off.

### B-5. Validate and report

Checklist — every item must pass:

- [ ] Every stage directory has `AGENTS.md`; every task has `skills/{task}/SKILL.md` with frontmatter.
- [ ] Every skill's Input Artifacts exist as outputs of an earlier skill or as stage inputs.
- [ ] Every artifact in every Mandatory Completion Protocol appears in the manifest's `STAGE_ARTIFACTS`.
- [ ] JSON structure blocks use snake_case and reference prior artifacts by ID fields.
- [ ] No Claude Code constructs remain (`SendMessage`, `Workflow`, `subagent_type`, `agentType`, `.claude/` paths, `model: opus` pins, `TeamCreate`).
- [ ] No `SKILL.md` body exceeds the target's skill length discipline (~500 lines).
- [ ] Scope-boundary sections exist per stage (the pattern's main defense against scope drift).

Then write `port-report.md`: source spec path/version or legacy source paths, stage plan, decisions from B-2 with rationale, what was converted vs. dropped vs. needs-human, and suggested smoke test (run stage 1 with a minimal input, verify all stage-1 artifacts parse as JSON). The report is the fidelity record; do not modify HarnessSpec merely to hide target-runtime limitations.

## Principles

- **Preserve design intelligence, replace runtime bindings.** Procedures, verification intent, evidence standards, and scope boundaries port; tools, paths, and collaboration protocols are re-emitted in target conventions.
- **The artifact contract is the contract.** All inter-step and inter-stage communication is files with documented JSON structure — never prose, never messaging.
- **Determinism lives outside the LLM.** Stage sequencing and completion checks live in Python; the agent controls only within-stage task order, which AGENTS.md pins.
- **One decision per concept.** Decide messaging, verification, and model policy once (B-2), then apply everywhere; mixed conventions are worse than either alternative.
- **Keep the change history alive.** If the source harness had a CLAUDE.md change-history table, carry it into the ported domain's README so the evolve loop can continue to operate.
